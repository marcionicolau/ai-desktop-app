# Feature Specification: Tagged Model Roles & Planner–Executor Fusion

**Feature Branch**: `004-model-roles-fusion`

**Created**: 2025-11-11

**Status**: Draft

**Input**: User description: "Criar a especificação completa para que a aplicação possa trabalhar com diferentes tipos de modelos para finalidades diferentes e trabalhando em conjunto como em um processo de fusão (modelo maior para planejamento + modelo menor para execução), use como base a configuração em /home/marcio/codes/cnpt/agents/legal-saas/config/litellm_config.yaml, as configurações, download dos modelos e ligação entre os modelos reais e as tags/etiquetas devem estar disponíveis na UI da aplicação"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Named Model Roles Bound to Real Models (Priority: P1)

The user defines named role tags — e.g. `planner`, `executor`, `writer`,
`extractor` — each representing a purpose in their workflow, and binds each
tag to a real model file from the local library. The tag (not the file) is
what conversations and features reference, so swapping the underlying model
later touches one binding, never the chat history or settings. Per-tag
generation settings (temperature, context intent, token budget) travel with
the tag. All of this is managed from the application UI: create/edit/delete
tags, bind/unbind model files, download a new model and assign it to a tag
in one flow.

**Why this priority**: The binding layer is the foundation everything else
sits on — without stable tag → model indirection there is no fusion, no
fallback, and no clean multi-model UX. It also delivers standalone value:
the existing chat can already target a tag ("load the `default` role")
instead of a raw filename.

**Independent Test**: Create a `writer` tag bound to any downloaded model,
mark it the default role, restart the app, and verify a normal chat reply
is generated by the bound model — with no fusion or fallback features
involved.

**Acceptance Scenarios**:

1. **Given** the roles panel, **When** the user creates a tag named
   `planner` and binds a downloaded model file to it, **Then** the tag
   persists across app restart and shows its bound model, file size, and
   quantization.
2. **Given** a tag bound to a model file, **When** the user rebinds the tag
   to a different model, **Then** subsequent generations through that tag
   use the new model without any other configuration change.
3. **Given** a tag, **When** the user sets per-tag generation overrides
   (temperature, max tokens), **Then** generations routed through that tag
   apply the overrides on top of global defaults.
4. **Given** no model is bound to a tag referenced by a feature, **When**
   the user opens that feature, **Then** a clear "unbound" state with an
   affordance to bind or download a model is shown — never a hard error.
5. **Given** the roles panel, **When** the user initiates a model download
   and selects a target tag, **Then** the model lands in the library and is
   automatically bound to that tag on completion.

### User Story 2 - Fusion Generation: Planner Thinks, Executor Answers (Priority: P2)

The user enables fusion mode on a conversation. Each user message then runs
a two-stage turn: the model bound to the planner role first produces a
concise plan (decomposition, constraints, draft structure), then the model
bound to the executor role produces the final streamed answer conditioned
on that plan. The streamed response visibly distinguishes the planning
phase from the answering phase. If either role is unbound, fusion mode
cannot be enabled and the UI explains which binding is missing.

**Why this priority**: Fusion is the headline capability the feature exists
for, but it strictly depends on US1 bindings; a user can already benefit
from tags without the pipeline. It is second in delivery order, not in
product value.

**Independent Test**: Bind `planner` to a larger model and `executor` to a
smaller model, enable fusion, send "outline then write a haiku about
compilers", and verify two distinguishable phases stream and the final
answer reflects the plan — fully testable without fallback configuration.

**Acceptance Scenarios**:

1. **Given** both planner and executor roles bound and fusion enabled,
   **When** the user sends a message, **Then** a planning phase produces a
   visible plan artifact followed by an answering phase that streams the
   final reply.
2. **Given** fusion enabled, **When** the executor phase generates,
   **Then** the planner output is included in the executor's prompt
   context (the executor does not re-plan from scratch).
3. **Given** the planner role unbound, **When** the user attempts to enable
   fusion, **Then** the toggle refuses with a message naming the missing
   binding and a shortcut to fix it.
4. **Given** a fusion turn in progress, **When** the user stops generation,
   **Then** the turn lands with whatever phases completed: plan-only keeps
   the plan visible and marks the answer partial.
5. **Given** a completed fusion turn, **When** the user regenerates,
   **Then** both phases re-run under the current bindings (a rebound
   executor changes only the answer phase's model).

### User Story 3 - Role Fallbacks and Per-Role Behavior (Priority: P3)

The user configures an ordered fallback for a role — e.g. `planner` falls
back to a smaller tag or raw model when the primary bound model fails to
load or errors mid-turn. Per-role defaults (sampling temperature suited to
the role's job, token budget, context hints) can be tuned independently of
the global settings, mirroring the per-alias tuning in the reference
configuration (planner at temperature 0.1, writer with a 16k context,
extractor at temperature 0.0).

**Why this priority**: Fallbacks matter on multi-model setups but are a
resilience refinement; the app already survives a single-model failure by
surfacing an error. Valuable, not blocking.

**Independent Test**: Bind `planner` to a model file, delete or corrupt
that file externally, configure `executor` as the fallback, run a fusion
turn, and verify the turn completes via the fallback with a visible
notice — tested without touching any other story's surface.

**Acceptance Scenarios**:

1. **Given** a role with a configured fallback and an unavailable primary
   model, **When** a generation routes through that role, **Then** the
   fallback model serves the turn and the UI records that a fallback was
   used.
2. **Given** a role whose primary and fallback are both unavailable,
   **When** generation routes through it, **Then** a typed error names the
   role and its attempted chain — the app never silently switches to an
   unrelated model.
3. **Given** per-role generation defaults, **When** a fusion turn runs,
   **Then** each phase applies its own role's settings (planner low
   temperature, executor normal) rather than the global values.

### Edge Cases

- A tag bound to a file that is deleted or corrupted externally → the tag
  lists as "broken binding" (file missing) and turns routed through it fall
  back or fail with a typed error, never crash.
- Deleting a tag that is referenced as a role (planner/executor/fallback)
  or as a conversation's active model → blocked with a naming error, or the
  reference is detached with an explicit confirmation; never a dangling
  pointer.
- Two roles bound to the same physical model file → allowed; a single load
  can serve both tags rather than loading the file twice in fusion mode
  (saves memory, no behavioral difference).
- Fusion where planner and executor are bound to the same model → allowed
  and degenerates to plan-then-answer on one model; no special-casing.
- The user rebinds a tag mid-generation → in-flight turn keeps the model it
  started with; the new binding applies to subsequent turns only.
- A downloaded model auto-bound to a tag that already had a binding → the
  new binding replaces the old only after the download completes
  successfully; a failed `.part` download never alters bindings.
- Very small models as planner (poor instruction following) → the planner
  output is still passed through; executor tolerance for a low-quality plan
  is accepted, but a plan that exceeds the prompt budget is truncated with
  the existing warning path.
- Tag name collisions/invalid input → tag names are unique, case-sensitive,
  slug-like (`[a-z0-9-]`); UI validates inline.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Users MUST be able to create, rename, and delete named model
  role tags from the UI; tag names MUST be unique and validated (lowercase
  slug characters only).
- **FR-002**: Users MUST be able to bind each tag to exactly one model file
  from the local library, rebind it, or leave it unbound; bindings MUST
  persist across restarts.
- **FR-003**: Each tag MUST support per-tag generation parameter overrides
  (same parameter set as global settings) that take precedence over global
  and per-model-file settings when a generation is routed through that tag.
- **FR-004**: The model download flow MUST allow assigning the incoming
  file to a tag, binding it automatically on successful completion;
  failed/partial downloads MUST NOT alter bindings.
- **FR-005**: The library and roles surfaces MUST show each tag's state:
  bound (model metadata visible), unbound, or broken (bound file missing).
- **FR-006**: A conversation MUST be able to enable fusion mode only when
  both a planner role and an executor role resolve to loadable models; the
  enforcement MUST surface which binding is missing.
- **FR-007**: A fusion turn MUST run the planner phase first, pass its
  output into the executor phase's prompt context, and stream both phases
  with a visible distinction between plan and answer.
- **FR-008**: Fusion turns MUST apply each role's own generation settings
  to its phase; stopping mid-turn preserves completed phases and marks the
  turn partial.
- **FR-009**: Users MUST be able to configure an ordered fallback chain for
  a role (other tags or specific models); an unavailable primary MUST
  cascade through the chain and record which candidate served the turn.
- **FR-010**: All feature entry points MUST reference models by tag, so
  rebinding a tag changes behavior app-wide without touching conversation
  data, settings, or code — the alias indirection of the reference
  configuration.
- **FR-011**: Two roles sharing one bound model file MUST be served by a
  single loaded instance (no double load); memory behavior MUST be
  documented when this sharing applies.
- **FR-012**: All existing guarantees MUST hold: typed-RPC only between
  renderer and main, single-flight generation per turn, FFI memory
  ownership rules, and offline operation (no cloud inference; downloads
  remain the only network feature).

### Key Entities

- **ModelTag**: a named role (unique slug name, display label, optional
  description of purpose); the indirection unit the whole app references.
- **TagBinding**: tag → model file mapping plus per-tag generation
  overrides; states: `bound | unbound | broken` (file missing).
- **FallbackChain**: ordered list of candidate tags/models attached to a
  tag, consulted when the primary binding is unavailable or errors.
- **FusionTurn**: a two-phase generation record on a conversation — plan
  artifact + answer, per-phase model/params/stats, partial/completion
  status.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user can create a tag, bind a downloaded model, and get a
  working reply through that tag in under 5 minutes from a fresh app
  launch, without editing any config file.
- **SC-002**: Rebinding a tag to a different model takes effect on the next
  turn with zero changes outside the roles panel (verified by swapping a
  tag between two visibly different models and observing the change).
- **SC-003**: A fusion turn on two bound roles completes with a visible
  plan phase and an answer phase that demonstrably uses the plan; the
  executor phase reuses warm KV context where the token prefix allows.
- **SC-004**: When a role's primary model is missing, a configured fallback
  serves the turn successfully and the UI records the fallback use — no
  user intervention required.
- **SC-005**: Two roles bound to the same model file consume one loaded
  model instance during fusion (verified via memory/load instrumentation),
  not two.
- **SC-006**: All existing gates pass (typecheck, lint, tests, builds) and
  no regression in single-model chat, downloads, or persistence.

## Assumptions

- The reference configuration (`litellm_config.yaml`) supplies the
  vocabulary and patterns — named aliases, per-alias params, ordered
  fallbacks — but the app keeps its own local model files and does NOT
  adopt LiteLLM, Ollama, or remote providers; everything stays offline.
- Fusion mode is opt-in per conversation; single-model chat remains the
  default and is unaffected when fusion roles are unbound.
- The planner role's output is a user-visible artifact (collapsible plan),
  not a hidden scratchpad — users chose "fusion" to see the thinking.
- Default tags `planner` and `executor` are provisioned on first run
  (unbound) so fusion has a predictable contract; additional tags
  (`writer`, `extractor`, …) are user-created.
- Two loaded models simultaneously is expected to fit on the target
  hardware for the documented small/large pairing; VRAM/RAM pressure is a
  user concern, but the UI warns when combined file sizes suggest it.
- A turn in flight is never re-routed: binding edits apply from the next
  turn (matches the existing single-flight and mid-generation rules).
