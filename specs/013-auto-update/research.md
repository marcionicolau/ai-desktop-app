# Research: Application Auto-Update (013)

**Status**: Complete — all technical unknowns resolved.

## D1 — Use Electrobun's built-in `Updater`; do not write a custom updater

**Decision**: Wrap the vendored devkit `Updater`
(`.hutch/devkit/api/sdks/main/core/Updater.ts`, exported via
`electrobun/main`) behind a thin `src/bun/updater/` service instead of
implementing check/download/apply ourselves.

**What the devkit already provides**:

- `Updater.checkForUpdate()` — fetches
  `{baseUrl}/{channel}-{os}-{arch}-update-v2.json` (falls back to the
  legacy `-update.json`), validates identity/channel/platform/arch,
  requires `artifact.tarSha256` integrity metadata in v2 manifests, and
  compares by bundle **hash** (`manifest.hash !== info.hash`), never
  semver.
- `Updater.downloadUpdate()` — delta patch-chain when available, full
  `.tar.zst` fallback; verifies `tarSha256`, stages via a native helper
  (`--prepare-update`), and publishes a durable
  `.electrobun-prepared-update.json` only after verification. Partial or
  corrupted downloads never produce a prepared record (FR-008).
- `Updater.applyUpdate()` — writes a native update plan, spawns the
  platform helper (detached child / Windows scheduled task), and quits
  through `requestQuitApproval` — cancelable by a before-quit handler,
  so apply is always user-initiated (FR-005).
- `Updater.onStatusChange(cb)` / `getStatusHistory()` — rich status
  entries (`checking`, `update-available`, `downloading`,
  `download-progress` with `bytesDownloaded`/`totalBytes`,
  `download-complete`, `applying`, `error`, `no-update`) that map
  cleanly onto the spec's update states.
- Dev-channel builds are self-disabled ("Dev channel - updates
  disabled") — dev is unaffected by definition.
- `prepareNativeUpdate` enforces HTTPS-only `baseUrl` **except**
  `http://localhost|127.0.0.1` — a local test feed over loopback is a
  supported configuration, which is how SC-002 end-to-end tests run.

**Rationale**: Reimplementing would duplicate ~2.5k lines of security
sensitive staging/apply logic (atomic publish, path validation, helper
handoff) that the framework already maintains.

## D2 — Feed format and publishing

**Decision**: The release feed is the Electrobun manifest convention;
the packaging workflow publishes feed assets to a single rolling GitHub
Release named `feed`.

- Manifest name: `{channel}-{os}-{arch}-update-v2.json`
  (e.g. `stable-linux-x64-update-v2.json`).
- Manifest schema (`UpdateManifestV1`, schemaVersion 1):
  `{ identifier, channel, version, hash, platform, arch,
     artifact: { file, tarSha256, tarSize } }`.
- With `release.baseUrl` set in `electrobun.config.ts`,
  `electrobun build --env=<channel>` writes the update manifest, the
  full artifact tarball, and (when `release.generatePatch` is enabled)
  delta patch files into the build output's `artifacts/` directory.
  Assets must be uploaded **unrenamed**.
- `release.baseUrl` is baked into `Resources/version.json` at build
  time; `Updater.getLocalInfo()` reads it at runtime.
- **Changelog**: the manifest has no changelog field. We publish a
  sidecar `{channel}-{os}-{arch}-notes.md` next to each manifest; the
  app fetches it when an update is available (FR-002). Content comes
  from `git log` between the previous tag of that channel and HEAD —
  generated by the release workflow step that already knows the tag.

## D3 — Feed hosting: rolling `feed` release on GitHub Releases

**Decision**: `release.baseUrl` =
`https://github.com/<owner>/<repo>/releases/download/feed`.

- GitHub Releases is a documented Electrobun baseUrl target. The
  standard `releases/latest/download` URL only tracks **stable**
  (`/latest` excludes prereleases) and gives one fixed tag segment — a
  single baseUrl cannot express two channels that way.
- The packaging workflow therefore maintains **one rolling release
  tagged `feed`** (marked prerelease, title "Update feed") whose assets
  are the union of all channel/platform manifests, artifacts, patches,
  and notes. Each tag build uploads with `gh release upload --clobber`,
  overwriting the assets for that channel/platform. Both channels share
  one baseUrl because the channel name is inside the filename.
- **Private-repo constraint (blocking)**: unauthenticated clients
  cannot download release assets from a private repository — the
  updater would always 404. V1 therefore requires **either** making the
  repo public (also unblocks branch protection) **or** pointing
  `release.baseUrl` at any static HTTPS host (S3/R2/Pages). The baseUrl
  is build-time config, so this is an ops decision, not a code fork;
  `UPDATE_FEED_BASE_URL` env overrides it for local/test builds, and
  `http://localhost` feeds work per D1. Failed resolution degrades
  silently per FR-007, so a private-repo build still functions exactly
  as today.
- Release feed is the only permitted network surface (FR-010) and is
  documented in `docs/` plus `AGENTS.md` (local-first exception).

## D4 — Channel selection: preferred channel drives the feed; cross-channel = guided install

**Decision**: A persisted `update.channel` preference (default = the
installed channel) selects which channel's manifest the update service
checks. Same-channel updates use the full built-in pipeline.
**Cross-channel transitions are a guided reinstall, not an in-place
update.**

**Why not in-place**: every layer of the devkit enforces
`channel === installed channel` — `prepareNativeUpdate` validates the
manifest against `info.channel`, and `loadPreparedUpdate` /
`validatePreparedUpdate` reject staged records whose channel differs.
Faking it would mean forking security-critical apply internals.
Rewriting `version.json` is unsafe (invalidates macOS code signatures;
needs elevated rights under Program Files).

**Flow**:

1. User picks stable or canary in Settings (FR-006); current version +
   channel are shown from `Updater.getLocalInfo()`.
2. The update service fetches `{preferred}-{platform}-update-v2.json`
   itself, validates with the exported `validateUpdateManifest`
   (`expected.channel = preferred`), and semver-guards against
   downgrades.
3. If `preferred == installed` and newer → `Updater.checkForUpdate()`
   (populates its private manifest) → `downloadUpdate()` →
   `applyUpdate()` on explicit restart.
4. If `preferred != installed` → the UI offers "Switch to
   `<channel>` `<version>`", which downloads that channel's **packaged
   installer artifact** (the same bundle the release job already
   uploads) to the user's Downloads folder and instructs to run it.
   The installed location/channel conventions
   (`~/.local/share/<identifier>/<channel>/`) keep both installs
   side-by-side without touching user data (FR-009).

This satisfies the spec's testable requirements — stable never offers
canary artifacts (feed-level separation), selection is honored and
visible — while keeping the in-place apply path entirely inside
verified framework mechanics.

## D5 — Verification model

**Decision**: SHA-256 integrity via the v2 manifest's `tarSha256`,
enforced by the native prepare helper before a prepared record is
published. Rejected artifacts surface as `error` status entries which
the service maps to the named RPC error `UPDATE_INVALID` (FR-004).

- `tarSha256` is mandatory in v2 manifests — `checkForUpdate` throws
  "archive integrity metadata is required" for legacy manifests without
  it.
- Signatures (minisign/GPG) are a stronger boundary but the devkit has
  no signature hook; spec accepts "signature **or** checksum". Noted as
  future hardening — the sidecar-notes channel can later carry a
  `.minisig` checked by our feed layer before handing off.

## D6 — Offline / failure semantics

- Check failure (network error, HTTP != 200, invalid JSON/manifest) →
  devkit emits `error` status; our service maps it to `idle`-like UI
  ("up to date" or silent) — never a blocking dialog (FR-007, SC-004).
- Launch check runs fire-and-forget after first paint; the 5-second
  budget (SC-001) is comfortably inside the devkit's 30 s fetch timeout.
- Interrupted downloads leave no prepared record; next
  `downloadUpdate()` re-runs cleanly (devkit re-checks existing
  prepared state first — resume of a *completed* stage is free).
- Apply never happens without an explicit `update.apply` request or an
  opted-in restart-on-quit preference (FR-005).

## D7 — Disable switch

**Decision**: `updates.enabled` setting (default `true` on packaged
canary/stable builds) + `AI_DESKTOP_APP_UPDATE=off` env kill-switch. When
disabled, the service short-circuits before any fetch — zero update
networking, app identical to a build without the feature.

## Alternatives considered

| Alternative | Rejected because |
|---|---|
| Custom updater over exported devkit helpers (`downloadResponseToFile`, `createNativeUpdatePlan`…) | Re-implements staging/apply security surface; still cannot legally cross channels without forking |
| One GitHub Release per version as feed | `releases/download/<tag>` is per-tag; `latest` excludes prereleases → no single stable+canary baseUrl |
| Rewriting `version.json` for channel switch | Breaks macOS signatures; elevated paths on Windows; fights the framework |
| Fetch changelog from GitHub Releases API | Private repo needs auth tokens in the client — credential exposure; sidecar notes file avoids it |
